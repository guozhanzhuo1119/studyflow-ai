# 04 接口设计（通俗版）

> 原标题：接口契约设计
> 一句话总结：**接口就是「点菜的规矩」——页面负责点，后端负责做；菜名、份量、忌口、出错怎么回话，全都提前写死，谁都不能临时改口。**

---

## 一、先理解「接口契约」是什么

前端的页面和后端的程序是两拨人（甚至可能是同一个人隔两周写），必须约定：

- 我叫什么菜（请求地址）
- 我要不要出示会员卡（鉴权）
- 菜里放不放辣（参数）
- 你端上来是什么样（响应格式）
- 卖完了怎么告诉我（错误码）

这份文档就是那张「菜单 + 后厨守则」。**页面能做到什么，取决于菜单上有没有这道菜。**

---

## 二、八条通用规矩（原文 4.1 的白话版）

| 规矩 | 原文说法 | 白话解释 |
|---|---|---|
| 统一入口 | Base URL `/api` | 所有菜都从同一个窗口点，不分一号窗口二号窗口 |
| 数据格式 | JSON / 表单 / 事件流 | 普通点菜用文字单；传文件用「附件」；聊天用「边做边端」 |
| 先验身份 | 除注册、登录、健康检查外都要令牌 | 除了办卡和问「你们营业吗」，其他都要出示会员卡 |
| 门票有效期 | JWT，7 天 | 会员卡 7 天有效，过期要重新办（见 P-04） |
| 回话格式 | `code / message / data / request_id` | 每次回话都说：成没成、为什么、东西在哪、这单的流水号 |
| 成功状态 | 一律 200 | 不管新建还是查询，都回「好的」，不搞 201/204 的花样 |
| 分页 | `page / size`，默认 20，最多 100 | 一次最多端 100 盘，多了自己翻页 |
| 没权限 | 一律回 404，不区分「不存在」和「不是你的」 | 不告诉小偷「这个抽屉存在但你打不开」 |

**「越权返回 404」这个细节值得保留**：它能防止别人通过错误码探测你有哪些数据。

## 三、出错时用户会看到什么（错误码白话表）

原文列了 20 多个错误码，对非技术读者只需要记住这几类：

| 用户看到的话 | 背后原因 | 页面该做什么 |
|---|---|---|
| 「内容不存在或已删除」 | 数据被删了，或者根本不是你的 | 退回上一页，不要停在空白页 |
| 「登录已过期，请重新登录」 | 会员卡过期 | 跳登录页，清掉本地状态 |
| 「该题缺少答案，不计入统计」 | 老题目没有录入答案 | 跳过这题，允许报错 |
| 「文件太大，最多 500MB」 | 上传超限 | 直接拦下，别让用户重试 |
| 「只支持 PDF / TXT / Markdown」 | 格式不对 | 提示支持的格式 |
| 「这份文件像是扫描件，读不出文字」 | PDF 是图片，没有文字层 | 建议换文件或先做 OCR |
| 「任务已入库，请去题库查看」 | 重复点了确认 | 直接跳题库，不报错 |
| 「操作太频繁，请稍后再试」 | 触发限流 | 显示倒计时，禁用按钮 |
| 「AI 暂时不可用，请稍后再试」 | 模型超时 | 给重试按钮，保留用户输入 |
| 「系统开小差了，编号 xxx」 | 未知错误 | 显示流水号，方便查日志 |

## 四、菜单上有哪些菜（按模块）

| 模块 | 代表性的菜 | 白话说明 |
|---|---|---|
| 账号 M1 | 注册、登录、查我是谁、登出 | 办卡、刷卡、查余额、退卡 |
| 目录 M2 | 科目 / 章节 / 知识点的增删改查、整棵树 | 管理楼层、房间、柜子 |
| 题库 M3 | 题目列表、详情、新增、编辑、删除、批量导入、变式题 | 管理柜子里的盒子 |
| 教材 M4 | 上传、列表、详情、删除 | 交货、查货、退货 |
| 任务 M5 | 查进度、任务历史、重试、看草稿、改草稿、确认入库 | 查加工进度、返工、验收 |
| 作答 M7 | 开始一轮练习、查进度、交答案、查历史、补错因、列表统计 | 开考、交卷、查成绩 |
| 学情 M8 | 总览、知识点掌握度、雷达图、错题本、标记已掌握、全量重算 | 成绩单、薄弱项、错题本 |
| 对话 M9 | 发消息（流式）、会话列表、历史消息、删会话 | 聊天 |
| 卡片 M10 | 我的卡片、点击、完成、忽略 | 收任务、领任务、交任务、拒绝 |
| 报错 M11 | 提交、我的报错、撤回、置修正/忽略、题级报错率 | 投诉、撤诉、结案 |
| 埋点 M12 | 批量上报（一次最多 20 条） | 记行为流水 |

## 五、三个关键场景，用「小故事」讲

### 故事一：上传一本教材

```
页面：我要传《高等数学.pdf》，属于「高数」科目   （multipart 表单）
后端：收到，先看大小（≤500MB）、看格式（pdf/txt/md）、算指纹
      → 如果这份文件你传过：直接告诉你「复用上次结果」，不重复花钱
      → 如果是扫描件：告诉你「读不出文字」，不建任务
      → 正常：给你一个任务号，后台开始干活
页面：拿到任务号，每 2 秒问一次「做到哪了」
```

### 故事二：交一道题

```
页面：会话 123，题 456，我选了 A、C
后端：先确认这题是你的 → 再确认这题有答案
      → 服务端自己判对错（不信页面传来的「我对了」）
      → 同一个会话同一道题只记一次分
      → 一个事务里同时更新：作答记录、错题本、掌握度、卡片状态
      → 回你：对不对、正确答案、解析、这题的历史正确率
页面：高亮对错、展开解析、按钮变「下一题」
```

### 故事三：和心月狐聊天

```
页面：发一句「我好焦虑，做不出来」
后端：先看学情（最近正确率、薄弱知识点、待复习数）
      → 判断意图：这是情绪表达
      → 先流式吐字（打字机效果），让用户马上看到回应
      → 同时组装一张卡片：从真实题库里挑 2 道最简单的题
      → 发一个 card 事件给页面
页面：显示卡片「去做 2 道简单的极限题」，点击 → 跳做题页
```

**注意**：卡片里的题目编号是后端挑的，不是模型编的——这是防「跳到不存在的题」的关键设计。

## 六、给非技术读者的两个要点

1. **接口文档决定页面能不能做**：比如文档里没有「刷新令牌」的接口，页面就做不到「7 天后自动续期」。
2. **错误码不是给用户看的**：用户只看到一句人话，错误码是给开发和日志用的。文档里「前端处理」那一列，才是产品体验的关键。

| **P-29** | 4.4 ① 上传 | 只写了 413/415 两种失败，没写「已达 20 份上限」「同一用户已有任务在跑」「触发限流」 | 补齐：`MATERIAL_LIMIT_REACHED`、`TASK_QUEUE_BUSY`、`RATE_LIMITED` |
| **P-30** | 4.5 状态枚举 | 题目有两套状态：`status`（todo/doing/done）和 `quality_status`（ok/flagged）。前端「未作答/已作答」筛选到底看哪个？文档说 status「不作为判分依据」 | 明确：页面筛选走作答记录聚合，不再用 `problems.status`；或直接删掉这个字段 |
