# 08 问题清单与修改建议

> 审查对象：01 技术选型、02 模块划分、03 数据模型、04 接口契约、05 核心流程、06 非功能约束、07 开发任务拆解
> 审查方式：逐份通读 + 七份交叉比对
> 结论先说：**整体设计思路是成熟的（尤其是幂等、确认入库、单一写入口），但存在 3 处「会直接做错」的硬伤、9 处「会导致返工」的矛盾、以及一批「读者看不懂」的表达问题。**

## 二、🔴 P0：必须先解决的硬伤

### P-01 外键两边长度不一致，建表就可能失败
- **位置**：03 · `materials.subject_id` 定义为 `CHAR(64)`；`subjects.id` 是 `CHAR(36)`
- **问题**：MySQL 要求外键两边的字符集和长度一致，否则建表直接报错；即便不建外键，数据也会对不上。
- **建议**：统一为 `CHAR(36)`。顺带全库检查一遍所有 `subject_id / chapter_id / kp_id` 的长度。

### P-02 主键规范不统一：36 位、64 位、自增三种混用
- **位置**：03 · `materials.id`、`material_chunks.id` 为 `CHAR(64)`；`subjects.id` 等为 `CHAR(36)`；`attempts.id`、`events.id` 为 `BIGINT AUTO_INCREMENT`
- **问题**：同一个系统里三种主键风格，前端无法统一处理，联调必踩；`materials.id CHAR(64)` 和 `problems.material_id CHAR(64)` 虽然自洽，但与其余表不一致。
- **建议**：定一条规则并写进 03 开头：**业务实体用 36 位 UUID；高频流水表（attempts、events、chat_messages）用自增 BIGINT**。然后统一改表。

### P-03 接口契约声称「id 统一 36 位」，与数据模型冲突
- **位置**：04 · 4.1「id 统一 36 位字符串」；03 里存在 64 位与自增
- **问题**：契约是前后端的法律，法律和实现不一致，前端会按 36 位写死。
- **建议**：把 4.1 改成「实体 id 为 36 位 UUID，流水 id 为整数；前端一律视为不透明字符串，不解析、不拼接」。这样两边都成立。

### P-11 多用户题库 + 全局向量索引 = 可能召回别人的题
- **位置**：01 · 1.5 FAISS；03 · 3.3「problems 不冗余 user_id」；06 · 6.4 归属校验
- **问题**：FAISS 索引是全库一个文件，检索本身**没有「按用户过滤」的能力**。题目表又不存 `user_id`，只能先召回再逐条查归属，可能出现「召回 10 条、9 条是别人的、过滤后不够用」，更糟的是如果过滤漏了就是数据泄露。
- **建议**（三选一，开发前必须定）：
  1. 索引元数据里带 `user_id`，检索时多召回再用元数据过滤（最简单，推荐）；
  2. 每个用户一个索引文件（隔离彻底，但文件多、内存碎）；
  3. 直接上 pgvector，用 SQL 的 `WHERE user_id = ?` 过滤（最干净，但要换库）。
- **验收补充**：加一条「用 A 的账号检索，返回结果 100% 属于 A」。

### P-31 确认入库的「标记已确认」在事务外，可能重复入库
- **位置**：05 · 5.1 确认段第 2 步写业务表（事务内），第 4 步才 `confirmed_at=now`（事务提交后）
- **问题**：如果第 4 步失败（进程崩溃、数据库瞬断），题目已经进库，但 `confirmed_at` 还是空。用户再点一次确认，校验通过 → **再写一套章节和题目**。
- **建议**：把「条件更新 `confirmed_at`」并入同一个事务，用 `UPDATE ... WHERE confirmed_at IS NULL` 判断是否抢到确认权；教材状态、索引更新可以事务后补偿。

### P-08 「一张表只有一个写入口」被自己打破
- **位置**：02 · 2.1 原则 vs 2.2 表格；05 · 5.2 第 2.5 步
- **问题**：原则说 `learning_stats` 只由 M8 写、`wrong_book_items` 归 M8；但 02 又说 M7 写错题本，05 说 M7 在事务里 upsert 掌握度。**三份文档三种说法**。
- **建议**：定为「M7 写 attempts / error_analyses；M7 在同一事务内调用 M8 的 `apply_result()`，由 M8 写 wrong_book_items 和 learning_stats」。然后同步改 02 的表格与 05 的流程。

### P-10 全篇都在说 `warnings`，但数据表里没有这个字段
- **位置**：05 · 5.1（跳过并记 warning、warnings 可见）；07 · D08/D10 验收；03 · `ingest_tasks` 无 warnings
- **问题**：警告信息无处落库，接口也无处返回。验收标准「失败知识点在 warnings 可见」无法通过。
- **建议**：`ingest_tasks` 增加 `warnings JSON`；`GET /tasks/{id}/draft` 响应增加 `warnings[]`；前端在草稿页展示「第 3 章第 2 节有 4 道题未生成」。

### P-16 worker 到底是线程还是进程，三处说法不同
- **位置**：01 · 1.7「进程内 worker」；02 · 2.3「解析 worker 若独立进程」；06 · 6.9「uvicorn 单 worker（FAISS 独占）」
- **问题**：这不是措辞问题——同进程线程会和「交卷 500ms」抢 CPU；独立进程又违反「FAISS 只能一个进程写」。
- **建议**：明确写「同进程内 1–2 个后台线程 + 任务表驱动；PDF 解析分片让出 CPU；索引只在 API 进程内更新」。并补一条「解析高峰期交卷 P95 仍 ≤500ms」的压测验收。

## 三、🟠 P1：会导致返工或体验问题

### P-04 JWT 7 天过期，但没有刷新机制
- **位置**：01 · 1.7「刷新不掉线」；04 · 4.1「有效期 7 天」；04 · 4.3 无 refresh 接口
- **影响**：第 8 天用户必被踢下线，与「不掉线」直接矛盾。
- **建议**：加 `POST /auth/refresh`（access 30 分钟 + refresh 7 天，refresh 存 httpOnly Cookie）；或老实改成「7 天内免登录」。

### P-05 五个时间数字互相打架
- **位置**：06 · 6.1「首响 ≤4s、首 token ≤2s」；06 · 6.8「LLM 超时 30s、首 token 15s」；04 · 4.4「SSE 总超时 60s」；01 · 1.6「首 token 延迟不可控」
- **影响**：开发不知道按哪个实现，测试不知道按哪个验收。
- **建议**：拆成三列写清楚——**目标 SLO**（首 token 2s / 首响 4s）、**软超时**（15s 走模板兜底）、**硬超时**（30s 报错，SSE 连接最长 60s）。

### P-06 没有数据库迁移框架，只有一次性脚本
- **位置**：01 · 1.2 落地提醒；03 · 3.7；07 · D01
- **影响**：这次能过，下次改表又要手写脚本、手动对顺序，迟早漏列。
- **建议**：引入 Alembic（半天成本），把 3.7 的建表顺序变成迁移版本；至少要把脚本纳入版本管理并写「执行前备份」。

### P-07 缓存键两种写法，删缓存会删空
- **位置**：05 · 5.2「删 `summary:{user_id}`」；06 · 6.6「`summary:{user_id}:{subject_id}`」
- **影响**：学情摘要 60 秒不更新，用户会看到「刚做完题，正确率没变」。
- **建议**：统一 key 模板并集中到一个 `cache_keys.py`；禁止业务代码手拼字符串。

### P-09 草稿字段：原则说 JSON，表里是 MEDIUMTEXT
- **位置**：03 · 3.1 原则 3、3.3 `draft_tree MEDIUMTEXT`、`draft_problems MEDIUMTEXT`
- **影响**：实现者不知道用 JSON 列还是文本列；`MEDIUMTEXT` 上限 16MB，而 06 规定草稿 ≤2MB，两处不一致。
- **建议**：统一为 `JSON` 类型，应用层做 2MB 校验；若担心 MySQL JSON 限制，就明确写「TEXT 存 JSON 字符串」，别两种说法并存。

### P-12 「五层目录」没有定义
- **位置**：02 · 全篇标题与 2.1；03 表结构；原型只有三层
- **影响**：读者按字面理解会以为是五个层级页面，实际是「科目/章节/知识点」+「母题/变题」。
- **建议**：明确为「三级目录（科目→章节→知识点）+ 题目两级（母题→变题）」，并在原型与文档统一叫法。

### P-18 「题目不冗余 user_id」与「万题 300ms」有冲突
- **位置**：03 · 3.3；06 · 6.1；06 · 6.4
- **影响**：列表查询要 join 4 张表验归属；交卷判分也要走同样链路，500ms 目标压力大。
- **建议**：要么接受并在压测中验证；要么在 `problems` 上冗余 `user_id`（写入时由服务层保证一致），换取查询性能。**这是一个明确的权衡，应该写出来，而不是只给结论。**

### P-19 标签用逗号字符串，没法按标签筛选
- **位置**：03 · `problems.tags VARCHAR(200)`；原型有筛选标签
- **影响**：「按标签筛题」只能全表 `LIKE`，直接违反 06 的性能红线。
- **建议**：改用 `problem_tags` 关联表，或用 JSON 数组 + 生成列 + 索引。

### P-14 删科目会删到什么程度，没定义
- **位置**：04 · `DELETE /subjects/{id}`「级联删除」；03 · 外键
- **影响**：可能把作答历史、错题本、学情一起清空，用户一年数据瞬间没了。
- **建议**：明确「删除科目 = 软删题目 + 保留作答审计；错题本与学情按科目清理」；接口返回删除计数并在前端二次确认。

### P-15 报错撤回后，无法再次置疑同一题
- **位置**：03 · `problem_reports` 唯一键 `(user_id, problem_id)`、状态含 `withdrawn`；04 · 撤回接口
- **影响**：撤回后再报同一题会合并到「已撤回」那条，永远无法重新置疑。
- **建议**：撤回改为删除记录（或把状态重置为 `pending` 并清空撤回时间），并在接口层说明。

### P-22 「放弃」算不算掌握度的分母
- **位置**：03 · `attempts.result` 含 `giveup`；05 · 掌握度公式「正确/总数」
- **影响**：同一份数据能算出两种掌握度，两个人都说自己对。
- **建议**：写死规则「放弃计入分母、不计正确」，并加一条验收用例（3 对 1 放弃 → 75%）。

### P-23 多张表缺 `updated_at`
- **位置**：03 · `problems`、`subjects`、`chapters`、`knowledge_points`
- **影响**：编辑后无法判断新旧，做增量同步、缓存失效、审计都没有依据。
- **建议**：凡是有编辑操作的表统一加 `updated_at`（`ON UPDATE CURRENT_TIMESTAMP`）。

### P-24 「除三个接口全鉴权」与「匿名埋点」矛盾
- **位置**：04 · 4.1 鉴权白名单；03 · `events.user_id` 可为空
- **影响**：未登录用户的埋点会被 401 拒掉，前端还会报错。
- **建议**：把 `/events` 加入白名单（允许匿名），或规定「未登录不埋点」并改表为 NN。

### P-27 题目详情接口会返回答案
- **位置**：04 · `GET /problems/{id}`「选项/答案/解析」
- **影响**：如果做题页也调它，学生可以直接看答案；即使页面不调，抓包也能看。
- **建议**：明确「做题只走 `/quiz/sessions` 的无答案清单」；详情接口加权限说明（仅题库管理/复盘），或增加 `?reveal=1` 才返回答案。

### P-28 交卷请求里保留客户端判分字段
- **位置**：04 · `POST /attempts` 的 `result`
- **影响**：虽然服务端会重判，但字段存在就一定会有人用；将来做多端时容易绕过判分。
- **建议**：标记废弃并计划删除；新契约只收 `selected_keys`。

### P-29 上传接口的失败场景没写全
- **位置**：04 · 4.4 ①
- **影响**：前端不知道「第 21 份教材」「已有任务在跑」「触发限流」该怎么提示。
- **建议**：补 `MATERIAL_LIMIT_REACHED`、`TASK_QUEUE_BUSY`、`RATE_LIMITED` 三个分支。

### P-30 题目有两套状态，语义重叠
- **位置**：03/04 · `problems.status`（todo/doing/done）与 `quality_status`（ok/flagged）；04 · 4.5 说 status「不作为判分依据」
- **影响**：前端「未作答/已作答」筛选到底看哪个？两套状态会打架。
- **建议**：删掉 `problems.status`，作答状态一律由 `attempts` 聚合得出；`quality_status` 保留。

### P-32 聊天接口没有校验会话归属
- **位置**：04 · `POST /chat` 接收 `session_id`；`GET /chat/sessions/{id}/messages`
- **影响**：如果实现时只按 id 查，可能读到别人的会话。
- **建议**：契约里明确「session_id 不属于当前用户 → 404」，并列为验收项。

### P-33 「连续答错 3 次」没有时间窗
- **位置**：05 · 5.3 触发规则
- **影响**：是 3 小时内、3 天内、还是历史任意连续三次？跨天怎么算？不同实现会得出完全不同的触发频率。
- **建议**：定义为「最近 7 天内、按作答时间排序的连续 3 次」，并写进接口与测试用例。

### P-34 一边说「物化避免聚合」，一边在事务里聚合
- **位置**：03 · `learning_stats` 设计说明；05 · 5.2 第 2.5 步（事务内更新掌握度与最近 10 次）
- **影响**：事务变长、锁持有变久，直接威胁 500ms 目标。
- **建议**：事务内只更新计数（正确数/总数/最近一次），`recent10` 与掌握度异步补算；或明确接受更长事务并调整 SLO。

### P-35 扫描件判定过于粗糙
- **位置**：05 · 5.1 同步段第 6 步「前 5 页平均每页 <20 字符」
- **影响**：扉页、目录、公式页、图表页都可能字符很少，正常书会被误判成扫描件。
- **建议**：改为「全文抽样 20 页 + 图片面积占比」综合判断，并提供「仍然继续解析」的强制入口。

### P-36 「不要把令牌写 localStorage」但没给方案
- **位置**：06 · 6.3
- **影响**：开发看到这句会卡住——不放 localStorage 放哪？最后还是会放。
- **建议**：明确方案（access 存内存 + refresh 存 httpOnly Cookie），或承认用 localStorage 并补 XSS 防护与令牌短有效期。

### P-37 不做移动端，与「学生刷题」场景冲突
- **位置**：06 · 6.10「≥1280 宽，不做移动端专项优化」
- **影响**：学生大量刷题场景在手机/平板，只做桌面会砍掉一半使用场景。
- **建议**：至少做到「手机上可用」（响应式 + 触控优化），或在 PRD 里明确「本产品定位为桌面学习工作台」，并说明理由。

### P-38 埋点容量与限流对不上
- **位置**：06 · 6.7「60 次/分、单批 20 条」 vs 03 · 3.8「每天 50–500 条」
- **影响**：按限流上限算，一天可上报数万条，容量估算差两个数量级，磁盘和归档策略会失准。
- **建议**：按「11 个事件 × 日均答题量」重算，给出峰值与日均两套数字。

### P-39 解析并发 2 与交卷 500ms 抢资源
- **位置**：06 · 6.2「全局解析并发 2」；05 · 5.2「交卷 ≤500ms」
- **影响**：PDF 抽取与向量化是 CPU 密集型，和 API 同机同进程时会直接拖慢交卷。
- **建议**：明确资源隔离方案（限制解析并发为 1、分片 sleep 让出、或独立进程 + 索引由 API 单写）；并加「解析高峰期交卷压测」。

### P-41 首屏 2 秒没有预算拆分
- **位置**：06 · 6.1
- **影响**：只有一个总目标，前端不知道 JS 该压到多少、接口该多快，最后无法定位是谁拖慢的。
- **建议**：给预算表：HTML 0.2s、JS/CSS 0.8s、接口 0.6s、渲染 0.4s；并注明测量环境（本地/公网 4G）。

### P-43 D14 的依赖漏了学情和卡片
- **位置**：07 · 7.3 D14 依赖写 D07/D09/D11，但验收要求统计与卡片
- **影响**：按依赖排期，前端会在 D12 完成前就「做完」，验收却过不了。
- **建议**：依赖补 D05、D12；或拆成「题库/做题页」与「学情/卡片页」两个任务分别验收。

### P-44 非功能指标写在前面，加固却排在最后
- **位置**：07 · D02/D04 验收含 401/404 与 500ms；D16 才是加固；M2 才验收非功能
- **影响**：前面阶段的验收根本过不了，只能「先欠着」，最后集中爆雷。
- **建议**：把「鉴权收口、索引、错误码、基础压测」前移到 M0；D16 只保留 nginx、限流、备份等运维项。

### P-47 16 个任务全是 P0，等于没有优先级
- **位置**：07 · 7.2 / 7.3
- **影响**：真出意外（人力不足、模型不稳）时，不知道该砍谁。
- **建议**：分成「必须演示」（D01–D05、D07–D09、D11、D14）与「可延后」（D06、D10、D12、D13、D15、D16 的非核心项）。

## 四、🟡 P2：一致性与表达问题

## 五、值得保留的四个好设计

评审不能只挑毛病，这四点建议原样保留：

1. **「确认后才入库」的草稿隔离**——把 AI 的不确定性挡在正式数据之外，这是整个方案最正确的决定。
2. **幂等键全部落在数据库**（文件指纹、四元组唯一键、`confirmed_at`）——比在代码里写 if 可靠得多。
3. **「每张表只有一个写入口」**（虽然执行有偏差，但原则本身是对的）——这是防止统计口径分叉的根本。
4. **失败矩阵 + 可验证的验收标准**——每条验收都能用一个请求、一次点击、一条 SQL 证明，不写空话。

## 七、一句话总结

> **这套文档的「设计判断」比「文档质量」好。**
> 该想的都想过了（幂等、事务、降级、频控、隔离），但七份文档像七个人各写各的：数字对不上、字段对不上、谁写哪张表对不上。
> 建议先花半天做一次「术语与数字对齐」，再花半天补三个方案（多用户检索隔离、令牌续期、worker 形态），这套设计就能真正落地。
