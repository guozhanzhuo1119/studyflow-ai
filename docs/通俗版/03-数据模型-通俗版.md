# 03 数据模型设计（通俗版）

> 原标题：数据模型设计
> 一句话总结：**19 张表就是 19 个抽屉，每个抽屉只放一类东西；抽屉之间用「挂钩」连起来，保证你永远不会拿到一份找不到主人的数据。**

---

## 一、用仓库来理解这 19 张表

想象你租了一个仓库：

- **房东** = `users`（用户）
- **楼层** = `subjects`（科目，比如「高等数学」）
- **房间** = `chapters`（章节）
- **柜子** = `knowledge_points`（知识点）
- **柜子里的盒子** = `problems`（题目）
- **盒子里的分装小包** = `variants`（同一道题的变式）
- **进出的货物** = `materials`（教材）、`material_chunks`（教材切成的文字块）
- **搬运工的工作单** = `ingest_tasks`（解析任务）
- **出入库流水** = `attempts`（每次作答）
- **账本** = `learning_stats`（掌握度）、`wrong_book_items`（错题本）

### 19 张表都装什么

| 分组 | 表 | 白话说明 | 一个用户大概多少条 |
|---|---|---|---|
| 身份与目录 | `users` | 账号 | 1 |
| | `subjects` | 科目 | 3–8 |
| | `chapters` | 章节 | 20–60 |
| | `knowledge_points` | 知识点 | 200–600 |
| 题库 | `problems` | 题目（题干、选项、答案、解析） | 1000–5000 |
| | `variants` | 变式题 | 母题的 0–3 倍 |
| 教材与任务 | `materials` | 上传的教材 | ≤20 |
| | `material_chunks` | 教材切块（按页/段） | 每份 100–2000 |
| | `ingest_tasks` | 解析任务与草稿 | 每月几十条，7 天清理 |
| 作答与学情 | `quiz_sessions` | 一次练习（一轮刷题） | 每天 1–10 |
| | `attempts` | 每道题的作答明细 | 每天 20–200 |
| | `error_analyses` | 错因分析 | 与错题同量级 |
| | `wrong_book_items` | 错题本条目 | 与错题同量级 |
| | `learning_stats` | 每个知识点的掌握度 | ≈ 知识点数量 |
| 对话与卡片 | `chat_sessions` | 一段对话 | 每月几十 |
| | `chat_messages` | 每一条消息 | 每段 10–100 |
| | `action_cards` | 行动卡片 | 每天 ≤2 |
| 反馈与埋点 | `problem_reports` | 题目报错 | 每周几条 |
| | `events` | 行为埋点 | 每天 50–500 |

> 合计：19 张，其中 3 张是旧表改造（`subjects`、`problems`、`materials` 等），10 张是新增。

## 二、五个关键设计，用「为什么」讲清楚

### ① 为什么题目表不存「用户 id」

题目的归属是**顺着链子推出来的**：题目 → 知识点 → 章节 → 科目 → 用户。

好处：不会出现「题目说属于 A，但它的章节属于 B」这种精分数据。
代价：每次查题都要多连几张表，所以文档在性能章节承诺了「万题 300ms」，这个承诺有压力（见 P-18）。

### ② 为什么「AI 生成的草稿」不单独建表

因为草稿只在「确认入库」之前存在，而且用户会反复改名、合并、删除。如果给草稿建表，就得维护「草稿表」和「正式表」两套结构，确认时还要做一次搬运，容易出错。

所以草稿直接以 JSON 文本存在任务表里，确认时一次性解析、一次性写进正式表。

### ③ 为什么掌握度要单独存一份

如果每次打开学情页都去算几万条作答记录，页面会卡。所以每次交卷时顺手把「这个知识点的正确率、最近 10 次正确率、掌握度」算好，存进 `learning_stats`。查的时候只读一行，很快。

代价：这份数据是「算出来的」，一旦算法改了或数据坏了，需要能全量重算（接口里留了 `/stats/recalculate`）。

### ④ 为什么到处都有「唯一键」

| 场景 | 唯一键 | 效果 |
|---|---|---|
| 同一用户同名科目 | 用户 + 科目名 | 不会出现两个「高等数学」 |
| 重复上传同一份文件 | 用户 + 文件指纹 | 第二次直接返回上次结果，不重复花 AI 的钱 |
| 重复交同一道题 | 用户 + 会话 + 题目 | 网络卡了连点两次，只算一次分 |
| 同一道题重复报错 | 用户 + 题目 | 合并成一条，计数 +1 |
| 重复点「确认入库」 | 确认时间非空 | 第二次返回「已入库」，不会生成两套题 |

**这是整套设计里最值钱的部分**：把「防重复」交给数据库，而不是靠代码里写 if 判断。

### ⑤ 为什么答案要存成数组

单选题的答案也存成 `["A"]`，多选题存 `["A","C"]`。这样判分逻辑只有一套：**两个集合完全相等才算对**。少选、多选、错选都算错。

## 三、数据量有多大（一个用户、一年）

| 项目 | 估算 | 说明 |
|---|---|---|
| 目录数据 | <1 MB | 几千行文字 |
| 题目（含解析） | 5–20 MB | 5000 题，平均每题 2–4 KB |
| 教材切块 | 20–100 MB | 20 份教材 |
| 作答记录 | 5–30 MB | 每天 20–200 条 |
| 埋点 | 20–80 MB | 需要按月归档 |
| 语义索引文件 | 15–30 MB | 5000 题 × 768 维 |

**真正的瓶颈是磁盘上的教材原文件**：20 份 × 最多 500MB ≈ 10GB。原文只提醒「要检查磁盘余量」，但没有给出总容量预算和清理策略，见 P-13。

## 四、给非技术读者的三个要点

1. **「草稿」和「正式题库」是物理隔离的**：AI 生成的东西先进任务表的草稿区，你点确认才搬进题库。
2. **删科目是很危险的操作**：文档写了「级联删除」，意味着一删就把下面的章节、知识点、题目全带走。但**作答记录、错题本要不要一起删，文档没写**（见 P-14），这会影响历史统计。
3. **数据是能自愈的**：语义索引文件丢了可以重建；掌握度算错了可以全量重算。真正不能丢的只有 MySQL 里的业务数据。

## 五、原文里的硬伤（按严重程度）

| 编号 | 位置 | 问题 | 影响 | 怎么改 |
|---|---|---|---|---|
| **P-01** | `materials.subject_id` 定义为 `CHAR(64)`，但 `subjects.id` 是 `CHAR(36)` | 外键两边长度不一致 | 建表可能直接失败，或数据对不上 | 统一为 `CHAR(36)`；建议全库 id 统一一种长度 |
| **P-02** | 04 文档说「id 统一 36 位字符串」，但 `materials.id`、`material_chunks.id` 是 `CHAR(64)`，`attempts.id` 是自增整数 | 契约与实现冲突 | 前端/接口层会困惑，联调必踩 | 明确「业务实体用 36 位 UUID，高频流水表用自增整数」，并在 04 改写措辞 |
| **P-10** | `ingest_tasks` 表没有 `warnings` 字段 | 但 05 流程多次说「跳过并记 warnings」「警告在 warnings 可见」，07 验收也要求可查 | 警告信息无处可存，前端看不到「哪几道题没生成」 | 加 `warnings JSON` 字段，或在草稿 JSON 里固定一个 `warnings` 节点并写进契约 |
| **P-09** | `draft_tree` / `draft_problems` 类型是 `MEDIUMTEXT`，但 3.1 原则说「用 JSON 承载」 | 表述不一致；`MEDIUMTEXT` 上限 16MB，而 06 又规定草稿 ≤2MB | 实现者不知道该用 JSON 列还是文本列 | 统一为 `JSON` 类型，并在应用层做 2MB 校验 |
| **P-14** | `DELETE /subjects/{id}`「级联删除」 | 没说是否删除 `attempts` / `wrong_book_items` / `learning_stats` | 删科目可能把历史统计一起清空，或留下孤儿数据 | 明确规则：题目软删或保留作答审计；统计随科目删除，作答记录保留 |
| **P-15** | `problem_reports` 唯一键 `(user_id, problem_id)` + 状态含 `withdrawn` | 撤回后用户想再报同一题，会命中旧记录合并到「已撤回」，无法重新置疑 | 报错功能出现死状态 | 撤回时删除记录，或改为「再次报错把状态重置为 pending」 |
| **P-22** | `attempts.result` 含 `giveup`，但掌握度公式写「正确数 / 总数」 | 「放弃」算不算分母没定义 | 同一份数据能算出两种掌握度 | 明确：放弃计入分母但不计正确；并在文档里写死 |
| **P-23** | `problems`、`subjects` 等表没有 `updated_at` | 编辑题目后无法判断新旧，缓存和同步没有依据 | 后续做增量同步、审计会缺字段 | 给需要编辑的表补 `updated_at` |
| **P-11** | 题目表刻意不冗余 `user_id` | 语义检索是全局索引，无法按用户过滤 | **可能把别人的题推给你**，属于数据隔离事故 | 见 01 文档同编号建议：索引带用户维度或分用户建索引 |
