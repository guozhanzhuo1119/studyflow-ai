# 06 非功能要求（通俗版）

> 原标题：非功能约束
> 一句话总结：**功能决定「能不能用」，非功能决定「好不好用、扛不扛得住、敢不敢给人看」。这一节全是「体验底线」和「安全底线」。**

---

## 一、性能：用户能感觉到的四个瞬间

| 瞬间 | 目标 | 用户的实际感受 | 做不到会怎样 |
|---|---|---|---|
| 点开页面 | ≤2 秒 | 坐下就能看见内容 | 以为网卡了，直接关掉 |
| 交一道题 | 0.5 秒内出结果 | 按下就有反馈 | 反复点提交，产生重复数据 |
| 和心月狐说话 | 2 秒内开始出字 | 像真人在打字 | 等十秒没动静，以为坏了 |
| 看题目列表 | 1 万题也不卡 | 翻页顺滑 | 越用越慢，最后弃用 |

**实现思路（白话版）**：
- 页面别一次把所有题都拉下来，分页、懒加载；
- 交卷只写 5 条记录，判分在内存里做，不查大表；
- 聊天边生成边往回吐，不要等整段生成完；
- 题目列表必须走索引，禁止用「包含关键词」这种全表扫。

**原文的「性能红线」值得保留**：不许模糊搜索、不许在代码里遍历全表、不许列表接口带大字段（题干全文、解析）。这三条是性能事故的高发区。

---

## 二、容量：这个东西最多能装多少

| 限制 | 数值 | 超了会怎样 | 白话解释 |
|---|---|---|---|
| 教材数量 | 每人最多 20 份 | 明确提示「先删旧的」 | 一个人一个学期大概就这么多书 |
| 单个文件 | 最多 500MB | 直接拒绝，不留残文件 | 超过这个大小，解析会跑到天荒地老 |
| 单份草稿 | 最多 2MB | 任务失败，建议分批 | 草稿太大，浏览器和数据库都难受 |
| 同时解析 | 每个用户 1 个，全局 2 个 | 排队 | 避免解析把服务器 CPU 吃光，导致做题卡顿 |
| 题库规模 | 1 万题不降级 | 超过要换检索方案 | 见 01 的演进顺序 |

**注意一个隐藏问题**：20 份 × 500MB ≈ 10GB，原文只提醒「注意磁盘余量」，没有给总容量预算、清理策略和用户提示。见 P-13。

## 三、安全：八道门锁

| 风险 | 措施 | 白话解释 |
|---|---|---|
| 密码泄露 | 用 bcrypt 加密存储，永不返回给前端 | 数据库被偷了也看不出原始密码 |
| 登录爆破 | 登录失败统一提示，不暴露「用户名是否存在」 | 不让坏人试探出你注册过没有 |
| 传输被窃听 | 生产环境全站 HTTPS | 路上有人偷看也看不懂 |
| 乱传文件 | 白名单 + 检查文件真实类型 + 改随机文件名 + 上传目录不可执行 | 防止有人传一个「伪装的程序」进来 |
| 路径穿越 | 存盘路径由服务器拼，不用用户文件名 | 防止 `../../` 这种路径攻击 |
| 页面注入 | 题干、解析、聊天内容渲染前先净化 | 防止有人在题目里塞一段脚本偷 cookie |
| SQL 注入 | 全部用参数化查询，不拼字符串 | 防止输入一段 SQL 把库删了 |
| 越权访问 | 除注册/登录/健康检查外全部验令牌；别人的数据一律返回「不存在」 | 一人一把钥匙，开不了别人的门 |

**原文有一条要求没给方案**：「前端不要把令牌写进 localStorage 明文」。但前后端分离 + Bearer 令牌，不放 localStorage 放哪？没有说。见 P-36。

## 四、数据隔离：A 绝不能看到 B 的数据

这是这类产品最容易出事故、也最不能妥协的地方。

- **每一层都要验归属**：科目看「是不是你的」；章节看它属于哪个科目；题目要顺着「题目 → 知识点 → 章节 → 科目」查上去。
- **越权统一返回 404**，不告诉对方「这东西存在但你不能看」。
- **AI 工具也要带用户身份**：所有查询都要加用户过滤，写操作要二次确认，确认人必须是本人。
- **数据库层兜底**：核心查询必须带 `user_id` 条件，禁止「查全表」的代码进业务。

> ⚠ 这里有个尚未解决的大坑：题目表故意不存 `user_id`（靠链条推归属），但语义检索用的是**全局索引**。检索时如何保证不把别人的题召回？原文没有答案。见 **P-11**，这是开发前必须定的问题。

## 五、日志与排障：出事能查

| 要求 | 白话解释 |
|---|---|
| 每个请求一个编号 | 用户报错时给出编号，开发能顺着编号找到完整经过 |
| 日志固定字段 | 时间、级别、编号、用户、接口、耗时、结果，一条不多一条不少 |
| 四条链路单独记 | 解析任务、聊天、判分、报错，各自带自己的业务编号 |
| 5xx 必须带编号 | 不允许「服务器错误」四个字了事 |
| 慢查询告警 | 超过 200 毫秒的 SQL 记一条警告 |
| 健康检查 | `/health` 看服务活着没；`/health/deep` 额外看数据库、Redis、索引文件、磁盘 |

## 六、缓存与限流：既要快，又要有节制

### 缓存（把常查的东西放手边）

| 缓存什么 | 多久过期 | 什么时候主动清 |
|---|---|---|
| 学情摘要 | 60 秒 | 交卷后 |
| 知识点统计 | 5 分钟 | 交卷后 |
| 科目树 | 5 分钟 | 增删改目录后 |
| 任务进度 | 10 分钟 | 任务结束 |
| 卡片频率计数 | 当天 / 4 小时 | 自然过期 |

**原则**：只缓存「算得出来的东西」，不缓存「真相」。缓存挂了就直查数据库，不能因为缓存挂了就不能答题。

### 限流（单位时间最多几次）

| 行为 | 限制 | 为什么 |
|---|---|---|
| 登录 | 每分钟 5 次 | 防撞库 |
| 注册 | 每小时 3 次 | 防批量注册 |
| 上传 | 每小时 5 次 | 防刷解析成本 |
| 聊天 | 每分钟 20 次 | 防刷模型调用 |
| 交卷 | 每分钟 120 次 | 正常做题碰不到 |
| 报错 | 每天 10 次 | 防恶意置疑 |
| 埋点 | 每分钟 60 次 | 超了静默丢弃 |
| 卡片 | 每天 2 张，同类 4 小时不重，忽略 2 次停 24 小时 | 防打扰 |

## 七、可靠性与备份：单机项目的诚实取舍

| 关注点 | 做法 |
|---|---|
| 重复操作 | 全部靠数据库唯一键拦住，不靠代码 if |
| 数据一致性 | 确认入库、交卷各自一个事务，失败整笔回滚 |
| 后台任务 | 状态机 + 最多重试 3 次 + 从失败阶段续跑 + 10 分钟超时巡查 |
| 索引文件 | 数据库是真相，索引坏了可重建；只允许一个进程写 |
| 外部依赖 | 模型超时走兜底或明确报错；Redis 挂了降级 |
| 备份 | 数据库每天全量 + binlog；文件和索引每周备份；每季度演练一次恢复 |

**原文主动承认的风险（这点很加分）**：没有高可用、没有自动故障转移、重启会中断正在处理的请求、不承诺 99.9% 可用性。**答辩时主动说清「为什么这样取舍」，比假装高可用更加分。**

## 八、部署与兼容性

- 一台服务器：nginx 负责对外（页面、接口转发、文件下载、500MB 上限），uvicorn 负责干活（**只能单进程**，因为索引文件只能一个人写）。
- 上传和聊天接口要关掉 nginx 的缓冲，否则会「一直等，最后一次性吐出来」。
- 启动顺序：建表 → 构建索引 → 启动定时任务 → 开始接客。索引失败不阻塞启动。
- 浏览器：Chrome / Edge 最新版，不支持 IE。
- 分辨率：≥1280 宽；**不做手机端**（这一点见 P-37，可能和真实用户场景冲突）。

## 九、验收清单（怎么证明做到了）

| # | 怎么试 | 通过标准 |
|---|---|---|
| 1 | 传一个 500MB 的文件 | 不崩、3 秒内给任务号；超大文件被拒 |
| 2 | 50 个人同时交卷 | 95% 在半秒内返回，且没有重复计分 |
| 3 | 把模型关掉再聊天 | 有兜底回复，标记 `fallback=true` |
| 4 | 用 A 的账号访问 B 的数据 | 全部 404；不带令牌访问业务接口全部 401 |
| 5 | 一分钟登录 6 次 | 第 6 次被限流；卡片第 3 次触发被拦 |
| 6 | 任务失败后重试 3 次 | 从失败阶段续跑；确认失败后题库无残留 |
| 7 | 制造一个 500 错误 | 响应里带请求编号，能查到完整日志 |
| 8 | 把 Redis 停掉 | 答题和聊天仍能用，不出现 500 |
| 9 | 把索引文件弄坏再启动 | 不崩溃，检索降级，重建后恢复 |

## 十、原文里的问题

| 编号 | 位置 | 问题 | 怎么改 |
|---|---|---|---|
| **P-36** | 6.3 令牌 | 要求「不要把令牌写进 localStorage 明文」，但没给替代方案。前后端分离 + Bearer 令牌，实际只有「内存 + 刷新令牌存 httpOnly Cookie」等少数做法 | 明确方案：access token 存内存、refresh token 存 httpOnly + Secure Cookie；或接受 localStorage 并加 XSS 防护，别只写一句要求 |
| **P-37** | 6.10 兼容性 | 明确「≥1280 宽、不做手机端」，但目标用户是学生，刷题的高频场景恰恰在手机/平板 | 至少做「移动端可用的响应式」；或在 PRD 里明确「只在电脑上学」，并说明为什么 |
| **P-38** | 6.7 埋点限流 vs 3.8 容量 | 埋点限流 60 次/分、单批 20 条，理论上每天可上报数万条；但容量估算写「每天 50–500 条」，差了两个数量级 | 按真实埋点密度重算（11 个事件 × 每次答题），并调整归档策略 |
| **P-39** | 6.2 并发 vs 6.1 性能 | 全局解析并发 2，而解析是 CPU 密集型（PDF 抽取 + 向量化）。如果和 API 同进程，会直接顶掉「交卷 500ms」的目标 | 明确资源隔离：解析限 1 并发 + 主动让出 CPU，或把 worker 拆成独立进程（但要注意索引单写约束） |
| **P-05** | 6.1 / 6.8 / 4.4 | 性能目标（首 token 2s、首响 4s）与超时阈值（15s、30s、60s）混在一起写，读者无法判断哪个是承诺、哪个是兜底 | 表格拆成两列：「目标 SLO」与「超时阈值」，并写清超时后走哪条兜底 |
| **P-40** | 6.3 / 全篇 | 没有任何「账号注销、数据导出」的设计，而这类产品面向学生、涉及个人信息 | 至少加「注销账号 + 删除全部数据」的接口与流程；导出可作为 P1 |
| **P-41** | 6.1 首屏 | 首屏 ≤2 秒没有拆分预算（HTML、JS、接口各占多少），也没有说明测的是本地还是公网 | 给出预算表：HTML 0.2s、JS 0.8s、接口 0.6s 等；明确测量环境 |
| **P-13** | 6.2 | 只给了「单用户 ≤20 份、单文件 500MB」，没给总磁盘预算与清理策略（与 03 容量章节同一问题） | 补：总容量 10GB 上限、超 80% 告警、30 天未访问教材提示清理 |
