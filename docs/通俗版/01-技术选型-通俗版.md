# 01 技术选型（通俗版）

> 原标题：技术选型
> 一句话总结：**这是一套「小团队、一台服务器、尽量不折腾」的工具组合。选型的核心不是先进，而是「已经会、够用、坏了能修」。**

---

## 一、先看这张「厨房设备清单」

把做产品类比成开一家小餐馆：不买中央厨房、不请外包团队，够用就行。

| 部位 | 用了什么 | 白话作用 | 为什么选它（白话） | 代价 / 限制 |
|---|---|---|---|---|
| 前端（用户看到的界面） | Vue 3 + Element Plus | 做页面、做表格和弹窗 | 项目里已经有了，换掉等于重做；组件现成，省时间 | 只能在电脑浏览器用，没做手机 App |
| 后端（干活的程序） | FastAPI（Python） | 接收请求、处理业务、调 AI | 上传大文件、流式聊天、跑 AI 都是它的强项；Python 的 AI 工具最全 | 只适合单机小规模，人多了要改架构 |
| 数据库（存数据） | MySQL 8 | 存用户、目录、题目、作答记录 | 数据关系强（科目→章节→知识点→题），需要事务保证「要么全成、要么全不成」 | 文本搜索弱；JSON 字段不能随便建索引 |
| 缓存 / 计数 / 锁 | Redis | 记频率、防重复、存临时进度 | 三个需求一次解决：计数、限时锁、高频查询缓存 | 重启可能丢数据，只能当「草稿纸」，不能当账本 |
| 语义检索（找相似题） | FAISS（本地索引文件） | 把题目按「意思」找出来 | 1 万题规模下足够快，不用额外装服务，一个文件搞定 | 只支持单进程写；没有按用户过滤的能力，这是隐患（见 P-11） |
| 大模型 | DeepSeek-Chat | 聊天、出题、判断意图 | 中文语气自然、支持结构化输出、便宜、换模型只改配置 | 网络依赖；输出可能不合格式；会编造内容 |
| 把文字变向量 | text2vec-base-chinese | 让「意思相近」可计算 | 中文短文本够用、CPU 就能跑、和现有索引匹配 | 对公式、符号、专业术语的理解一般 |
| 读 PDF | PyMuPDF | 把 PDF 里的字抽出来 | 快、能拿到字号和位置，用来推断章节 | 扫描版（图片）读不出字，本期不做 OCR |
| 后台任务 | 程序内自带的后台线程 + 数据库任务表 | 慢慢解析教材，不卡住页面 | 单机、量小，不需要额外的任务系统 | 进程重启会中断；「线程还是进程」文档里没写清，见 P-16 |
| 文件存储 | 服务器本地文件夹 | 存上传的教材 | 零成本、够用 | 换机器要手动搬；磁盘满了会传不上去 |
| 登录凭证 | JWT | 一张 7 天有效的电子门票 | 前后端分离场景标配 | **7 天后必须重新登录，文档却说「不掉线」，没有续期接口，见 P-04** |
| 部署 | nginx + uvicorn | 一个对外接待，一个在里面干活 | 已验证能处理大文件上传和页面路由 | 只能单进程跑（因为索引文件只能一个人写） |
| 日志 | JSON 格式日志 + 请求编号 | 出问题能顺着编号查 | 不依赖任何监控平台 | 没有大盘和告警，只能翻日志 |

## 二、为什么「不选更好的」

原文花了很大篇幅解释「为什么不选 XX」，其实可以归成三句话：

1. **能沿用就不换**：换框架的迁移成本，远大于它带来的那点好处。
2. **规模没到，不要提前上重型装备**：1 万道题用不上向量数据库集群，就像家里做饭不需要商用冷库。
3. **一个人维护不了的东西，再先进也是负债**：微服务、消息队列、多智能体，出问题时没人兜底。

原文明确「本期不做」的清单：微服务、Kafka、Elasticsearch、GraphQL、多 API 进程、LangGraph、多 Agent。**这个克制是对的，建议保留。**

---

## 三、给非技术读者的三个要点

1. **这套东西一台普通服务器就能跑**，不需要云原生、不需要容器编排（Docker/K8s 都留到以后）。
2. **换 AI 模型不用改代码**，只改一个地址和一个模型名——这是选 DeepSeek 兼容协议带来的好处，避免被厂商锁死。
3. **真正的上限不在数据库，在磁盘和索引方式**：教材最多 20 份 × 500MB ≈ 10GB；题库超过 10 万题、或者要做到「多人数据强隔离」，就得换检索方案（把 FAISS 换成 pgvector，顺带换 PostgreSQL）。

## 四、原文里站不住脚的地方

| 编号 | 位置 | 问题 | 怎么改 |
|---|---|---|---|
| P-04 | 1.7 认证一节 | 写「JWT + bcrypt，刷新不掉线」，但接口文档写的是「7 天有效期」，也没有刷新令牌接口。**7 天后用户必然被踢下线**，与「不掉线」矛盾 | 要么加 `POST /auth/refresh`（推荐），要么把「不掉线」改成「7 天内免登录」 |
| P-11 | 1.5 向量库 | FAISS 是全库一个索引，但题库按用户隔离。检索时怎么保证不把 B 的题推给 A？原文只说「归属按 user_id 判定」，没说检索层怎么过滤 | 索引里带上 `user_id` 元数据、检索后过滤；或每个用户一个索引文件；或直接上 pgvector 用 SQL 过滤。**这条必须在开发前定** |
| P-16 | 1.7 异步任务 / 6.9 部署 | 一处说「进程内 worker」，一处说「解析 worker 若独立进程」，一处说「单 worker（FAISS 独占）」。到底是线程还是进程？两种做法对并发和稳定性的影响完全不同 | 明确成「同进程内的后台线程池」，并说明它和「交卷 500ms」如何互不干扰（比如限制并发为 1–2、PDF 解析让出 CPU） |
| P-06 | 1.2 / 3.7 | 承认「没有 Alembic，靠建表语句自动创建，需要一次性迁移脚本」。一次性脚本能解决这次升级，但**下一次改表还会重演** | 本期就引入 Alembic（半天工作量），或至少把迁移脚本纳入版本管理并写清执行顺序 |
| P-19 | 1.3 / 3.3 | 题目标签用逗号分隔的字符串存（`tags VARCHAR(200)`），但产品需要按标签筛选 | 改成关联表或 MySQL 8 的 JSON + 生成列索引；否则「按标签筛选」只能全表扫 |
