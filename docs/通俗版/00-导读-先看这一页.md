# 先读这一页：StudyFlow AI 是什么、这套文档怎么读

> 这份导读是给「不写代码的人」准备的。看完这一页，你就能和别人讲清楚这个产品要做什么、七份文档分别在说什么、以及哪些地方还没想明白。

---

## 一、一句话说清这个产品

**StudyFlow AI 是一个「会陪你把书读薄」的学习工具。**

你把教材 PDF 传进去，它帮你把书拆成章节、知识点和题目；你刷题时它自动判对错、记错题、算掌握度；当你学崩了、说「我好焦虑做不出来」时，它会先安抚你，再递给你一张**小到不可能拒绝的任务卡**——比如「去做 2 道简单的极限题」，点一下就直接开始做。

它不是「聊天机器人 + 题库」的拼装，而是想让**「情绪崩掉」这个最常见的弃学原因**有一个具体的出口。

---

## 二、谁会用它、怎么用

| 角色 | 场景 | 他关心什么 |
|---|---|---|
| 备考的学生（主要用户） | 晚上打开电脑，传一本教材，刷 20 道题，卡住了找 AI | 题对不对、我哪里弱、我还能不能坚持 |
| 自己（开发者/答辩者） | 演示从「上传教材」到「做题 → 学情 → 情绪陪伴」的完整闭环 | 能不能现场跑通、说不说得清取舍 |

**注意**：文档里写的都是「单用户、单机部署」，也就是**一个人用、一台服务器跑**，不是给全班、全校用的系统。这个前提贯穿全部七份文档。

## 三、产品的三条主线（记住这三条就够了）

```
主线 A：教材 → 题目
  传 PDF → 后台慢慢解析（几分钟）→ 生成「草稿」→ 你确认，才真正进题库
  关键：AI 出的题在你点确认之前，一道都不会进正式题库。

主线 B：做题 → 学情
  开始一轮练习 → 交答案 → 服务器判对错（0.5 秒内）→ 同时更新错题本和掌握度
  关键：重复提交不会重复计分。

主线 C：情绪 → 卡片 → 回来做题
  你说「我焦虑」→ 心月狐安抚 → 递一张 2 道题的小卡片 → 点进去做 → 做完自动销卡
  关键：模型不能自己编题目编号，卡片指向的题必须是真实存在的。
```

三条主线之外还有一条小支线：**题目报错**（你觉得答案不对 → 报错 → 这题暂时下架 → 修正后恢复）。

## 四、七份文档分别在讲什么

用开一家小餐馆打比方：

| 文档 | 讲什么 | 餐馆类比 | 谁该读 |
|---|---|---|---|
| 01 技术选型 | 用什么工具、为什么不用别的 | 买什么灶、什么冰箱 | 技术 |
| 02 模块划分 | 系统拆成几块、各管什么 | 后厨分工：切菜、炒菜、收银 | 技术 + 产品 |
| 03 数据模型 | 数据存在哪、怎么存 | 仓库货架怎么摆 | 技术 |
| 04 接口设计 | 前端和后端怎么对话 | 服务员怎么把菜单传进后厨 | 技术 |
| 05 核心流程 | 一件事从头到尾怎么走 | 一道菜从点单到上桌 | **所有人**（最能看懂产品） |
| 06 非功能要求 | 速度、安全、容量、备份 | 卫生标准、出餐速度、消防 | 技术 + 答辩 |
| 07 开发计划 | 先做什么后做什么 | 装修施工排期 | 所有人 |

**如果你只想花 10 分钟了解这个项目**：读这份导读 + 05 核心流程 + 07 开发计划。

## 五、关键数字一页纸

| 项目 | 数值 | 白话解释 |
|---|---|---|
| 部署方式 | 单机、单进程 | 一台服务器、一个程序，挂了就挂了，不承诺 24 小时不停 |
| 开发人力 | 1–2 人 | 所以刻意不引入微服务、消息队列、多智能体 |
| 题库规模 | 1 万题以内 | 超过 10 万题才需要换检索引擎 |
| 单个教材 | ≤500MB、最多 20 份 | 大概 10GB 磁盘上限，文档里没算总账 |
| 交卷响应 | P95 ≤500 毫秒 | 100 次交卷里 95 次在半秒内返回 |
| 首屏 | ≤2 秒 | 点开页面到能看见内容 |
| AI 首次开口 | 目标 ≤2 秒，超时阈值却是 15 秒 | **两个数字对不上，见问题清单 P-05** |
| 卡片频率 | 每天最多 2 张，同类 4 小时不重复 | 防止变成烦人的推送 |
| 数据表 | 19 张 | 3 张是旧表改造，10 张是新增 |

## 六、术语小词典（看文档卡住时回来查）

| 词 | 一句白话 |
|---|---|
| 接口 / API | 前端和后端约定好的「对话方式」，像餐厅的菜单编号 |
| 契约 | 双方都签字认账的格式，改之前必须通知对方 |
| 幂等 | 同一个操作做 10 次，结果和做 1 次一样（交卷重复提交不会加 10 分） |
| 事务 | 一组操作要么全成功、要么全失败，不能只做一半 |
| 外键 | 两张表之间的「挂钩」，保证不会出现找不到归属的数据 |
| 索引 | 书的目录，让数据库不用一页页翻 |
| JSON | 一种「键值对」格式，适合存结构不固定的东西（比如选项列表） |
| 缓存 | 把常查的结果先放手边，省得每次都问数据库 |
| 限流 / 频控 | 限制单位时间内的次数，防止刷爆或打扰 |
| SSE | 服务器像水龙头一样一点点往回吐字，聊天才有「打字机」效果 |
| 向量 / FAISS | 把题目变成一串数字，按「意思相近」找题；FAISS 是本地检索引擎 |
| Embedding | 把文字变成数字向量的过程，语义相近的向量距离近 |
| RAG | 先检索资料再让模型回答，减少胡编 |
| P95 | 100 次里有 95 次达到这个水平，用来描述「大多数时候的体验」 |
| 物化 | 把算好的统计结果单独存一张表，查的时候不用现算 |
| 草稿 / 确认入库 | AI 生成的题先放在「待审核区」，你点头才进正式题库 |
| JWT | 一张带签名的「电子门票」，7 天有效 |
| worker | 后台打杂的程序，负责慢慢解析教材，不占用你点页面的时间 |
| OOM | 内存被撑爆，程序直接崩 |
| 越权 | A 用户看到了 B 用户的数据，这是严重事故 |

## 七、这套文档目前最大的三个问题（先给你打个预防针）

1. **前后数字对不上**：AI 首响有 2 秒、4 秒、15 秒、30 秒、60 秒五种说法；ID 长度有 36 位和 64 位两种写法；缓存键有两种写法。详见问题清单 P-05、P-02、P-07。
2. **几个关键设计只有结论、没有落地路径**：比如「多用户题库怎么保证 AI 检索不串数据」「JWT 7 天过期后怎么续期」「草稿里的警告信息存在哪」，文档都没写。详见 P-11、P-09、P-10。
3. **开发计划没有工期**：16 个 P0 任务、1–2 个人，既没有排期也没有人力估算，按现在的写法无法判断能不能做完。详见 P-17。

> 具体的修改建议在 **08-问题清单与修改建议.md**，按「必须改 / 建议改 / 可选优化」三档分级，每条都写清了在哪一段、为什么是问题、怎么改。
