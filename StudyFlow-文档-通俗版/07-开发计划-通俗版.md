# 07 开发计划（通俗版）

> 原标题：开发任务拆解
> 一句话总结：**先打地基（数据、登录、判分），再通水电（上传、出题、对话），最后装修（页面、埋点、加固）。一共 16 个必做任务，分三道验收门。**

---

## 一、三个阶段，像盖房子

| 阶段 | 名字 | 干什么 | 出口标准（过不了不许进下一阶段） |
|---|---|---|---|
| Phase 0 | 打地基 | 改数据表、收口登录、题目能判分、学情能查、日志能追 | 两个账号互相看不见数据；同一题重复提交只算一次；任何错误能顺着编号查到日志 |
| Phase 1 | 通水电 + 装修 | 上传、解析、出题、对话、卡片、报错、前端、埋点、加固 | 现场能完整演示：传教材 → 确认入库 → 做题 → 看学情 → 聊情绪 → 领卡片 → 做完 → 报错 |
| Phase 2 | 可选升级 | 雷达图、报错处理页、多选判分、复习排期、换检索引擎 | 按优先级排，不影响主闭环 |

---

## 二、地基阶段（6 个任务，全部 P0）

| 编号 | 干什么（白话） | 为什么必须先做 | 怎么算做完（能验证） |
|---|---|---|---|
| D01 | 把 19 张表建好，写一个一次性升级脚本 | 后面的功能全都建立在表结构上 | 老库跑完脚本能正常启动；脚本重复跑不出错；老数据能挂到一个「种子账号」下 |
| D02 | 所有接口都验身份，所有数据都验归属 | 不先做，后面每个功能都要返工 | 不带令牌一律 401；A 访问 B 的数据一律 404 |
| D03 | 题目加上「题型、选项、答案、解析」，前端能正常显示 | 没有答案就无法判分 | 新老题目都能显示；选项顺序稳定；无答案题提交返回「缺答案」且不计分 |
| D04 | 做题会话 + 服务端判分 + 防重复提交 | 这是产品的核心动作 | 同一题重复提交只算一次；单选多选判分正确；进度数字正确 |
| D05 | 学情统计 + 错题本 | 情绪卡片要靠它挑题 | 交卷后立刻能查到更新；做题少于 3 道显示「数据不足」；连对 3 次标记掌握 |
| D06 | 统一错误码 + 请求编号 + 四条链路日志 | 出问题能查，否则后面全是黑盒 | 任何 500 都带编号；能用编号串起一次完整请求 |

## 三、闭环阶段（10 个任务，全部 P0）

| 编号 | 干什么（白话） | 依赖 | 怎么算做完 |
|---|---|---|---|
| D07 | 教材上传：500MB、边收边存、算指纹去重、识别扫描件 | D02 | 500MB 不崩、3 秒给任务号；重复上传直接复用；扫描件给出建议 |
| D08 | 后台任务：进度、重试、锁、超时巡查 | D07 | 状态只能顺序推进；进度可见；失败能重试 3 次并从失败阶段续跑；杀进程重启不会永久卡住 |
| D09 | 草稿编辑 + 确认入库（一个事务 + 更新索引） | D08 | 确认前题库 0 新增；确认后一次写入；重复确认返回 409；中途出错整笔回滚；索引失败有标记 |
| D10 | AI 出题：格式校验、答案必填、去重、题量上限 | D08 | 每题都过格式校验；答案非空；重复题跳过；单知识点 ≤20 题；失败只影响该知识点 |
| D11 | 心月狐对话：流式输出、注入学情、判断意图、兜底 | D05 | 能依次收到开始/文字/卡片/结束；模型挂了有兜底；回复能提到你的薄弱点 |
| D12 | 行动卡片：规则、频率、目标校验、状态流转、完成回流 | D11 | 每天 ≤2 张；同类 4 小时不重；忽略 2 次停 24 小时；卡片指向的题都真实存在；做完自动销卡 |
| D13 | 报错通道：合并计数、置疑、撤回、恢复 | D03 | 同人同题只 1 行；报错后退出推荐；24 小时内可撤回；超时撤回返回 409 |
| D14 | 前端落地：题库页、做题页、知识库页、登录页 + 悬浮球 | D07/D09/D11 | 原型里的跳转真实可用；数据全部来自真接口（不是假数据）；聊天能出卡片并跳做题页 |
| D15 | 埋点：11 个事件 + 批量上报 | D06 | 11 个事件都能在表里查到；一次最多 20 条；匿名上报不报错 |
| D16 | 加固：nginx、限流、缓存、磁盘守卫、备份脚本 | D09/D12 | 第 6 节的 9 条验收全过；限流生效；Redis 停掉不影响答题 |

## 四、依赖顺序（照着做就不会返工）

```
D01 数据表
├─ D02 登录鉴权 ── D06 日志/错误码 ── D15 埋点
│    └─ D07 上传 ── D08 任务 ── D09 确认入库 ── D14 前端
│                        └─ D10 出题
├─ D03 题目模型 ── D04 判分/幂等 ── D05 学情/错题 ── D11 对话 ── D12 卡片
│                    └─ D13 报错
D16 加固：依赖 D09 / D12
```

**可以并行的**：D10 出题 与 D05 学情 / D11 对话可以同时做；D13 报错在 D03 完成后就能开工；D15 埋点在 D06 之后随时插。

## 五、三道验收门

| 门 | 包含任务 | 过门标准（白话） |
|---|---|---|
| M0 地基可用 | D01–D06 | 两个账号数据互不可见；题目能判分、重复提交不重复计分；学情能查；错误能追 |
| M1 闭环可演示 | D07–D15 | 现场从传教材演到报错，中间不断链；所有数据来自真接口 |
| M2 可上线 | D16 | 9 条非功能验收全过；备份能真正恢复一次 |

## 六、最容易翻车的五件事（原文写得很实在，建议保留）

| 风险 | 表现 | 对策 |
|---|---|---|
| AI 出的题质量不稳 | 答案和解析对不上、一道题多个正确答案 | 格式校验 + 答案必填 + 人工确认 + 统计采纳率，不追求全自动 |
| 500MB 上传 | 一次性读进内存直接崩 | 边收边写盘 + 字节计数 + nginx 和应用双端限制；先用 50MB 压测再放大 |
| 流式被 nginx 缓冲 | 前端一直等，最后一次性吐出来 | 关缓冲、加心跳、放宽读超时；先用命令行验证流式 |
| 索引并发写 | 新题搜不到，甚至索引损坏 | 只允许一个进程写 + 确认后同步 + 启动重建 + 脏标记 |
| 掌握度算法反复改 | 今天这样算、明天那样算，数据无法比较 | 先按一版公式落地并写明「口径待确认」，跑通后再调参数 |

## 七、给非技术读者的三个要点

1. **16 个 P0 任务不是「16 天」**：原文没有给任何工期和人力估算，这是这份计划最大的缺口（见 P-17）。
2. **顺序比速度重要**：D01/D02 不做完就写页面，后面一定返工。原文「先数据、后接口、再前端」的原则是对的。
3. **「能演示」是硬标准**：每个任务的验收都写成「能用一个请求 / 一次点击 / 一条 SQL 证明」，不写「完成 XX 功能」这种空话——这一点值得保留。
